# Contributing to FTorch

Thank you for your interest in contributing to FTorch. Contributions of all
kinds are welcome, from bug reports and feature requests to documentation and
code. This document explains how to get involved and what we expect of pull
requests.


## Ways to contribute

- **Report a bug or request a feature** by
  [opening an issue](https://github.com/Cambridge-ICCS/FTorch/issues). Please
  search the existing issues first to avoid duplicates.
- **Contribute code or documentation** by
  [forking the repository](https://github.com/Cambridge-ICCS/FTorch/fork),
  making your changes on a branch, and opening a pull request.
- **Help others** by answering questions in issues and discussions.

For anything beyond a small fix we encourage you to open (or comment on) an
issue before starting work, so that the approach can be agreed in advance.

Everyone participating in the project is expected to follow the
[code of conduct](README.md#code-of-conduct).


## Development quick reference

Full details can be found in the
[online developer guide](https://cambridge-iccs.github.io/FTorch/page/developer/developer.html).
The essentials are collected here.

Install the development tools (preprocessor, linters, testing utilities) using the
`dev` dependency group of the `ftorch_utils` package:

```sh
pip install . --group dev
```

Build FTorch with its test suite and run the tests:

```sh
mkdir build && cd build
cmake .. -DCMAKE_BUILD_TYPE=Release -DCMAKE_BUILD_TESTS=TRUE \
         -DCMAKE_PREFIX_PATH=</path/to/torch/installation>
cmake --build .
ctest --verbose
```

Running the unit tests additionally requires
[pFUnit](https://github.com/Goddard-Fortran-Ecosystem/pFUnit); see the
[testing documentation](https://cambridge-iccs.github.io/FTorch/page/developer/testing.html).

Code should be checked with the project's linting tools before submission.
These checks are run in CI on all pull requests. All except ShellCheck can be
installed with pip as part of the `dev` dependency group:

- Fortran: [fortitude](https://github.com/PlasmaFAIR/fortitude)
- C/C++: [clang-format](https://clang.llvm.org/docs/ClangFormat.html) and
  [clang-tidy](https://clang.llvm.org/extra/clang-tidy/)
- Python: [ruff](https://docs.astral.sh/ruff/)
- Shell: [ShellCheck](https://github.com/koalaman/shellcheck)
- CMake: cmake-lint from [cmake-format](https://github.com/cheshirekow/cmake_format)
- GitHub Actions workflows: [zizmor](https://woodruffw.github.io/zizmor)

If you believe a particular rule should not apply to your change, please
justify this in the pull request.

> [!NOTE]
> `src/ftorch_tensor.f90` and `src/ftorch_test_utils.f90` are generated by the
> [Fypp](https://fypp.readthedocs.io/) preprocessor. Edit the corresponding
> `.fypp` files and regenerate; never edit the generated `.f90` files directly.
> A pre-commit hook in `.githooks/` can be used to check that the two stay in
> sync.


## Pull request expectations

Please ensure that your pull request:

- has a clear description of what it does and why;
- is focused, with a clean diff: no unrelated changes, dead code, or leftover
  debugging output;
- includes tests covering any new or changed behaviour;
- updates documentation (in-code comments and pages under `pages/`) where
  relevant;
- adds an entry to `CHANGELOG.md` for notable changes such as new features,
  bugfixes, and dependency updates;
- passes the static analysis checks listed above.

By submitting a pull request you agree that your contribution is made available
under the project's [MIT licence](LICENSE).


## Use of generative AI

Contributions developed with the assistance of generative AI tools are
accepted, subject to the following conditions:

- All other guidance in this document applies in full. In particular, you are
  expected to have reviewed and understood the code yourself, to have built and
  run it (including the tests), and to have produced a clean diff as described
  above.
- You will make follow-up changes to your contribution/Pull-Request to address any
  review comments and meet the maintainers' requirements for merging.
- The pull request text must clearly explain what you have done, and must
  include a brief statement disclosing which models you used and for what
  tasks.

We reserve the right to close any pull request that we do not feel is ready for
review and would take excessive reviewer time, or to ask that the above
conditions are met prior to a proper review.
